Known-flaky/broken tests exist in this repo, confirmed unrelated to the changes that surfaced them (reproduced in isolation, and against a clean `git stash`'d checkout):

1. **`apps/admin/test/layouts/default.spec.ts`** — "switches locale text and persists the choice via cookie". Fails intermittently under full-suite parallel `vitest run` (timing-sensitive `setTimeout(resolve, 50)` after a locale-toggle click). Update 2026-08-14 (during `visitor-analytics`): no longer reliably passes in isolation either — reproduced failing via `npx vitest run test/layouts/default.spec.ts` alone, and confirmed via a clean `git stash` re-run (fails identically with zero of that change's edits applied, including an `AppSidebar.vue` edit that touches this exact test's rendered output). Treat as flaky at any run granularity now, not just under full-suite parallelism.

2. **`e2e/tests/auth.spec.ts`** — "create a City and see it in the list". `getByText('Velence')` is an ambiguous Playwright locator: it matches both the newly-created city row AND the app's own toolbar title "VelencEvents Admin" (contains "Velence" as a substring). Fails reliably, not flaky — this is a real bug in the test's locator, not a race condition. The fix (not yet applied by anyone) would be to scope the locator more precisely, e.g. `page.getByRole('cell', { name: 'Velence', exact: true })` or similar.

3. **`e2e/tests/registration.spec.ts:9`** and **`e2e/tests/venue-admin-creation.spec.ts:8`** — both time out identically at `page.getByLabel('Venue name (EN)').fill(...)`: "element is not visible". Both flows fill a venue-name field that lives inside a `LocaleTabs` HU/EN tab pair, and the EN-slot input apparently never becomes visible/actionable for Playwright even though `LocaleTabs.vue`'s `v-window-item`s are documented as rendering `eager` specifically to avoid this. Confirmed pre-existing 2026-08-10 (during `api-contract-hardening`) via a clean `git stash` re-run — fails identically with zero of that change's edits applied. Root cause not investigated. `admin-user-editor.spec.ts`'s `createTargetUser` helper deliberately routes through organiser creation instead of venue creation to sidestep this exact bug (its own comment names it).

4. **`apps/backend` — `MediaResourceIT.validJpegUploadIsAcceptedAndPersisted`** — asserts the upload response's `url` field is not null, but it's always null. Fails reliably (not timing-flaky), not intermittent. Confirmed pre-existing 2026-08-11 (during `public-read-contract-corrections`) via a clean `git stash` re-run of just this test — fails identically with zero of that change's edits applied (the change never touches `media/`). **Root cause confirmed 2026-08-21** (during `analytics-visitor-identity`), no longer a guess: `MediaResponse.java` is `public record MediaResponse(UUID id) {}` — there is no `url` component at all, so `MediaResourceIT.java:64`'s `.body("url", notNullValue())` can never pass under any ordering or timing. The `admin-media-bff` change removed `MediaResponse.url` ("backend no longer builds media URLs") and left this one assertion behind. **The fix is deleting that single assertion line** — the surrounding test is otherwise valid and its `Media` entity assertions pass. Still not fixed; out of scope for every change that has hit it so far. Reproduced 2026-08-20 (`venue-auto-approval`, 311/312) and 2026-08-21 (`analytics-visitor-identity`, `mvnw verify` 349 tests, sole failure).

5. **`apps/admin/test/utils/eventApproval.spec.ts`** — "Hook timed out in 10000ms" inside `@nuxt/test-utils`'s `setupNuxt()`. Only occurs under full-suite parallel `vitest run`; passes cleanly in isolation (`npx vitest run test/utils/eventApproval.spec.ts` — 5/5 pass). Same category as #1 (Nuxt test-environment setup racing under parallel workers), just a different file. Confirmed 2026-08-20 during `venue-auto-approval`, which never touched this file.

6. **`apps/public` — the whole suite under `npm run test`.** Same `setupNuxt()` 10s hook timeout as #5, but it takes out *all six* test files at once, reporting `6 failed / 32 skipped` — which looks catastrophic and is not. Six Nuxt environments starting concurrently exceed the hook timeout. **`npx vitest run --no-file-parallelism` passes 6/6, 32/32.** Confirmed 2026-08-21 during `analytics-visitor-identity`. Reach for `--no-file-parallelism` before believing a public-suite mass failure.

7. **Not a test bug — check disk space first.** On 2026-08-21 the dev host hit 100% disk (78G full, 565M free) and produced three convincing-looking but spurious failures in one session: Postgres dying mid-`mvnw verify` with `Connection refused`, a Playwright run failing with `ENOSPC: no space left on device` + `Page crashed`, and vitest hook timeouts. `df -h /` takes a second and rules this out. Biggest consumers on this machine were `~/.gradle` (8G), `/var` (9G), `~/.npm` (3.6G), `~/snap` (3.1G) — all caches, but never delete without asking.

**Why:** Found while verifying the full suite passes at the end of various changes. None of the flagged tests touch the code paths those changes actually modified.

**How to apply:** If any of these tests fails during a future `/opsx:apply` or CI run, don't assume your own changes broke it — check whether it's one of these first, and confirm via a clean-checkout re-run if genuinely uncertain (stash your changes, re-run just the failing test, unstash). None have been fixed. Fixing #2's locator or investigating #3's `LocaleTabs` interaction bug are legitimate, low-risk cleanups if a future session has spare scope, but out of scope for any change that doesn't already touch that area.
